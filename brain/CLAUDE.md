# Vault — Instructions for Claude Code

## What is this vault
Knowledge base for **{{PROJECT_NAME}}**. Persistent memory across sessions.

## Folder structure

- `Features/` — one note per feature; tracks status from idea to shipped (the ticket system)
- `Metrics/` — session and feature productivity reports (auto-generated by `/save`)
- `Architecture/` — system overview, service boundaries, data flow diagrams
- `Codebase/` — conventions, patterns, key modules, known gotchas
- `Database/` — schema, relationships, indexes, migration notes
- `Install/` — local setup steps, required env vars, dependency notes
- `Decisions/` — ADRs — the *why* behind non-obvious choices
- `APIs/` — external integrations, auth methods, rate limits, gotchas
- `Infra/` — Docker, Terraform, CI/CD, environment configs
- `Runbook/` — deploy steps, rollback procedure, production debug guide

## Zettelkasten Rules

### Note creation
- Use wikilinks: [[note-name]] (not markdown links)
- Mandatory YAML frontmatter on every note
- Filenames in kebab-case: `auth-flow.md`, not `Auth Flow.md`
- 1 concept per permanent note (atomicity)
- Minimum 2 wikilinks per note (dense linking)

### Standard frontmatter
---
title: Note Name
tags: [project, topic]
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: active
type: permanent
---

### Feature ticket lifecycle (Features/ folder)
`status: draft` → `ready` → `in-progress` → `shipped` → `archived`

Each feature note links to its spec in `docs/superpowers/specs/` and tracks task progress inline.

### Never do
- Don't delete notes without asking
- Don't use markdown links for internal notes (use wikilinks)
- Don't create notes without frontmatter
- Don't change folder structure without documenting it
- **NEVER write secret values** — only references, never actual tokens/passwords
- **NEVER git push** — commits yes, push is done by the user

## Session Commands

### /save
When you receive this command:
1. Update affected notes (append/edit, never rewrite)
2. Add wikilinks between created/modified notes
3. **Generate session metrics** — run `scripts/metric-logger.sh report` and save the output as `brain/Metrics/session-YYYY-MM-DD-<branch>.md` with a brief human-readable summary at the top
4. **If a Feature ticket changed to `status: shipped` this session** — run `scripts/metric-logger.sh feature-report <feature-name>` and save the comparison as `brain/Metrics/<feature-name>-comparison.md`. Tell the user they can run `/churn` to visualize all features
5. `git commit` (NO push — push is done by the user)

The user never needs to run metric commands manually — `/save` handles everything.
