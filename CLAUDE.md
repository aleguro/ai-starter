## Agents (`.claude/agents/`)

Agents are autonomous sub-agents with restricted toolsets. Use them via the `Agent` tool or by name in Claude Code.

| Agent | Role | Invoke when |
|-------|------|-------------|
| `playwright-test-planner` | Explores the live UI + source → produces a TC-NN test plan | New feature needs E2E coverage |
| `playwright-test-generator` | Takes a plan → drives scenarios in browser → writes `.spec.ts` | After planner produces a plan |
| `playwright-test-healer` | Debugs and fixes red specs (surgical edits only) | CI goes red / spec breaks after a frontend change |

**Why agents and not skills?** Each has a different toolset (planner needs browser exploration, generator needs Write/Edit, healer needs debug tools) and each starts with isolated context — the generator doesn't need the planner's full exploration history, only its output plan.

### Automatic stack detection

When the user asks to work on a file, load the stack skill based on the directory:
- `apps/rails-app/**` → load `rails`
- `apps/react-app/**` → load `react`
- `services/python-service/**` → load `python`

## Brain (Obsidian vault)

The vault lives in `./brain/`. Each folder has an `index.md` — start there before reading individual notes.

| Folder | What goes in it |
|--------|-----------------|
| `Features/` | One note per feature — the ticket system (status, tasks, links to spec) |
| `Metrics/` | Session and feature productivity reports — auto-generated by `/save` |
| `Architecture/` | System overview, service boundaries, data flow diagrams |
| `Codebase/` | Conventions, patterns, key modules, known gotchas |
| `Database/` | Schema, relationships, indexes, migration notes |
| `Install/` | Local setup steps, required env vars, dependency notes |
| `Decisions/` | ADRs — record the *why* behind non-obvious choices |
| `APIs/` | External integrations, auth methods, rate limits, gotchas |
| `Infra/` | Docker, Terraform, CI/CD, environment configs |
| `Runbook/` | Deploy steps, rollback procedure, production debug guide |

### When to update which folder

- Starting a new feature → create ticket in `Features/`
- Touching schema or running migrations → update `Database/`
- Adding/changing an external integration → update `APIs/`
- Making a non-obvious tech decision → add an ADR to `Decisions/`
- Changing setup steps → update `Install/`
- Refactoring a module's structure → update `Codebase/`
- Changing infra, Docker, CI/CD config → update `Infra/`

### /save

On receiving `/save`:
1. Identify which brain folders are affected by the current work
2. Update (or create) the relevant notes with wikilinks between them
3. `git commit` in brain (no push — the user pushes)

## Rules

- **NEVER `git push`** directly — use `git push-pr` (`scripts/push-pr.sh`)
- No secrets in code — use `.env` (in `.gitignore`)
- No features without a spec — use `spec-driven-development`
- No code outside the spec's scope — `spec_drift > 10%` → stop and review
- No functions > 40 lines without tests — `ai_blob_score > 20` → refactor
- Run `graphify query` before touching code in any module

## Sub-agent orchestration

### Model routing per SDD phase

| Phase | Mode | Model | Effort | Why |
|-------|------|-------|--------|-----|
| Spec writing | Slow | Opus | high | Deep business reasoning, ambiguity to resolve |
| Graphify context | Fast | Haiku | low | Read-only lookups |
| TDD loop | Fast | Sonnet | medium | Fast red→green iteration, scope pinned by spec |
| Refactor | Fast | Sonnet | medium | Mechanical transformations, low ambiguity |
| Code review | Slow | Sonnet | high | Multi-file reasoning, worth catching subtle issues |
| Spec drift check | Fast | Haiku | low | Diff analysis |

### When to parallelize

**Condition:** two or more tasks in the same stage target different stacks (rails ≠ react ≠ python).

```
Stage 1:
  T1.1 Stack: rails  ─┐
  T1.2 Stack: react  ─┤→ launch in parallel (separate worktrees)
  T1.3 Stack: python ─┘
```

**How to launch parallel agents in Claude Code:**

```
For each independent task:
  Agent(subagent_type: "fresh", isolation: "worktree",
        model: "sonnet",
        prompt: "Implement T1.x: <desc>. Load <stack> skill.
                 Run tdd-loop. Commit feat(T1.x): <desc>.")
```

Wait for all agents to complete before starting Stage 2.

**Sequential (same stack or dependent tasks):** run one at a time, same session.

### Context strategy

- **Fork** (inherits full conversation): spec writing, graphify exploration — needs business context
- **Fresh** (starts clean): TDD loop, refactor, code review — needs only the code

## Standard workflow

```
/ship-feature → driver skill, coordinates all 5 layers below:
1. spec    → spec-driven-development (Feature ticket + actors, UCs, stages, tasks)
2. api     → tdd-loop per backend-contract task
3. app     → tdd-loop per UI/consumer task
4. qa      → playwright-test-planner → playwright-test-generator → playwright-test-healer
5. stats   → /save (brain update + metrics) → git push-pr
```

Each layer ends in exactly one commit, gated on `ai_blob_score` / `spec_drift` (see `.claude/skills/driver/SKILL.md`) before the driver advances to the next layer. The layers can still be run by hand one at a time — the driver is the default, not the only path.

**What's automatic (no manual steps):**
- graphify updates after every `git commit` (post-commit hook)
- Session metrics saved to `brain/Metrics/` on every `/save`
- Feature AI vs human report generated on `/save` when a feature is shipped
- `/churn` to visualize all features whenever you want

**The only manual inputs:** `Human: Xh` estimates on tasks (5 sec each), committing code, saying `/save`.

| Spec generation | `playwright-test-generator` | sonnet | Drive scenarios + write code |
